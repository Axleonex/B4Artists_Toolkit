# Plan 02-02: configuration, capability model and migration

**Goal:** A small validated model for every tool's presentation and slider options.
**Architecture:** Pure JSON codec/model plus package-aware preferences; no new
scene-wide setting duplicates. **Tech stack:** Python dataclasses/dicts, JSON, RNA.
**Execution:** Sequential tasks; depend on a passing fresh baseline.

## Task 1: define the capability registry

**Create:** anim_assist/ui/timeline_config.py, tests/test_timeline_config.py.
**Modify:** ui/timeline_catalog.py (presentation metadata only).

**Do:** Define SLIDER_CAPABILITIES for eight IDs in the design table, units,
neutral/default/range, eligible modes, adapter key and supported options.
Keep ACTIONS IDs/operator suffixes/fixed arguments unchanged. Separate
TOOLBAR_FAMILY_ORDER from historical catalogue/menu order. All 89 tools can
be Hidden/Button; only the eight scalar entries can be Inline/Popout. OFFSET
uses Button/session settings. Record unsupported overshoot/settings explicitly.
Finite numeric validation rejects NaN/infinity, min>=max and nonpositive timing
scale. Tool hard limits derive from inspected math, not mockup endpoints.

**Verify:** Test 89 IDs, eight eligible slider IDs, fixed dispatcher mapping
parity with baseline and nonnumeric-mode rejection. Compile/import the pure
module without bpy; constants can be passed into model helpers if necessary.

**Done means:** The configuration cannot create a fake slider or mislabel units.

## Task 2: define active layout and library schema

**Do:** Version 1 JSON record: schema_version, active layout object, active saved
ID (or custom), saved layout list. Layout contains id/name, family/tool order,
tool entries `{action, mode, label_mode, width, range_min, range_max, default,
sensitivity, precision, snap_enabled, snap_step, presets, overshoot_enabled}`.
Only supported scalar fields apply. No current gesture value, scene pointers,
animation, target, clipboard or rig state is serialized. IDs are generated
independently of names. Canonical normalization is deterministic/idempotent.
Read old versions through migration, reject unsupported future schemas without
overwriting saved data, skip unknown action IDs with visible warnings while
retaining their raw records for future compatibility. Limits prevent unbounded
preferences payloads. Resolve missing tools to safe Hidden, not auto-visible.

**Verify:** Tests for JSON roundtrip, invalid enum/type/numeric range, empty
configuration, unknown tool, future schema and preservation on rejection.

**Done means:** Validated persistence has a stable shape independent of UI text.

## Task 3: add recommended defaults and one-time migration

**Modify:** prefs.py, __init__.py (only registration needed for preference record).

**Do:** Add a versioned StringProperty record and migration marker using get_prefs.
Fresh Recommended: DRAG/SMOOTH Inline; B25/B50/B75, NUDGE_LEFT/RIGHT,
COPY_KEYS/PASTE_KEYS, MIRROR_SELECTED, BAKE_STEP, TRAIL_SHOW Button;
SCALE_DRAG Popout; all other actions Hidden in the row, reachable in More/Search.
Initialize before overlay registration. Old explicitly saved Boolean selections
map eligible entries to Popout, ordinary entries to Button; unchecked stays
Hidden, empty stays empty, row-hidden stays hidden. Detect default-only legacy
state using explicitly set RNA fields rather than guessing from matching values.
Never recreate/reset on every enable. Keep old fields readable for prior exports.
Preference updates redraw only; user-save behavior follows host preferences.

**Verify:** Tests: fresh has two inline controls, same old custom/empty/hidden
selection after migration, migration idempotent, renamed extension package can
resolve preferences, redraw does not touch data, invalid JSON leaves backup intact.

**Done means:** New users get a focused row; existing users retain their choices.
